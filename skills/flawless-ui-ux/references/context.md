# Context

Use this reference when a new surface, substantial redesign, or missing project knowledge requires a brief. For a small change, recover only the facts that affect it.

## Establish the job

Find the visitor, the situation, and the decision or action the interface supports. Replace broad labels with an observable outcome: an operator locating a failed payment needs different information from a buyer comparing subscriptions.

Inspect the requested route or component and its immediate surroundings. Look for existing product documentation, design tokens, shared components, content sources, and representative states. A missing design document does not erase the visual system evident in the implementation.

Keep a working brief with only useful information:

- Target, audience, user task, and desired outcome.
- Existing identity and the decisions the request allows changing.
- Content, facts, and assets available for this surface.
- Stack, component conventions, data constraints, and relevant platform behavior.
- Consequential unknowns and what evidence would resolve them.

Reuse an established brief instead of writing it again. Preserve language, locale, units, and terminology unless changing them is part of the request.

## Separate facts from assumptions

Treat supplied product facts, current data sources, and confirmed requirements as constraints. Inconsistent sources are an uncertainty to resolve, not permission to invent a convenient answer.

Make low-impact layout and demonstration choices when the brief leaves room. Identify sample product details that must be confirmed. Do not turn sample figures into performance claims, customer counts, testimonials, or certifications. For data-heavy work, distinguish zero, missing, loading, and failed data before deciding how to display them.

Ask a focused question when an unknown changes the product's claim, the permitted redesign, or a consequential user action. Continue independent work that does not depend on the answer. Do not delay a clear task to ask for routine aesthetic preferences that can be inferred from the project.

## Inventory usable material

Inspect the actual assets before planning around them. A filename is not evidence that a picture is suitable or that a screenshot depicts the current product.

| Available material | Useful design opportunity |
|---|---|
| Actual product UI or output | Demonstrate the result or the task directly |
| Product photography, location, materials, or process | Make the subject recognizable and support a specific claim |
| Brand typography, marks, and printed artifacts | Establish composition and visual roles grounded in the brand |
| Real operational data | Build a screen around a useful question and honest comparisons |
| Mostly text | Use structure, editing, hierarchy, and proportion to communicate confidently |

Use supplied imagery first when it serves the purpose. Search or generate assets only if the capability and task permit it. Check the source and usage terms of found assets, preserve required credits, and do not present a generic photograph as the client's actual team, premises, or product.

## Set the preservation boundary

For refinement, identify the identity, functioning behavior, and content outside the named target. For redesign, separate the visual choices being replaced from the workflows, routes, terminology, and facts that remain valid.

Example: replacing a checkout's visual hierarchy does not authorize changing its tax calculation or removing an existing payment option. Improving a dashboard's density does not authorize omitting inconvenient records.

Carry only the relevant decisions into [Direction](direction.md). Reuse existing project records for durable decisions when documentation is part of the work; do not create a new hidden state directory or a mandatory brief file for every request.

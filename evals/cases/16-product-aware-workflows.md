# 16 Product-aware workflows

Status: prepared; all agent/model outcomes remain pending. Runtime fixtures are evaluated separately by automated tests. Use the [manual kit](../README.md) for isolation, versions, matching conditions, evidence, and reporting.

## Continuity across tasks

Use an independent copy of the dashboard fixture. Ask the agent to refine one view and preserve the product facts, then record only useful product/design decisions in Markdown. In a fresh session, ask for a related change without restating those choices. Check actual document reads, preserved decisions, and whether sources or assumptions are misrepresented. Change a linked source and check whether the affected choice is reviewed rather than silently treated as current. Documentation is task-specific, not a mandatory questionnaire.

## Existing-interface refinement

Use independent copies of the same dashboard or brand-page starting revision for the 1.1.0 release, 2.0 candidate, and no-skill baseline. Keep the prompt, host, model, reasoning, tools, and permissions matched. Request a specific readability or hierarchy improvement. Record concrete improvements, identity, facts, function, scope, time, actual reads, and unnecessary questions. Preserve first outputs and unsuccessful attempts.

## Explicit interaction evidence

Copy the workflows fixture into a disposable project, serve it locally with an existing permitted tool, and use its actual URL. Ask the agent to inspect the member-editor flow, explain step/state evidence, correct a controlled local defect, and verify under equivalent conditions. The flow file must be explicitly selected on both runs. Keep the same flow when fixing the application; changed flows need new baselines. Missing controls/states and blocked steps are not corrections. Observe keyboard focus, entered test data, close/recovery behavior, and verification limits.

## Several screens

Use independent copies of two related existing screens or two permitted routes. Select them explicitly and request consistency review. Keep intentional differences such as primary/secondary actions and heading roles. Record whether reported variants are useful, corresponding states are compared, and semantic decisions follow the product's Markdown context. A lower variant count alone is not success.

## Evidence

Record skill revision, host/model/settings, prompts, tool versions, active plugins, isolation limits, document reads, elapsed time, source changes, matching screenshots, run manifests, and unresolved observations. Mark criteria met, failed, or unobserved. These runs establish evidence only when executed; prepared cases do not establish improved design or lower latency.
